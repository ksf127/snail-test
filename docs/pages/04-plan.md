# 04 盘前计划

> 页签 `index.html#tab-plan`；接口 `GET /plans`、`POST /plans`、`POST /plans/{id}/cancel`；表 `t_trade_plan`；成交侧关联字段 `t_trade.plan_id`、`t_trade.is_planned`。

## 1. 这页回答什么（不回答什么）

回答：

- 某段时间准备了哪些「若 X 则 Y」，触发条件、动作、依据分别写了什么；
- 哪条待触发、哪条已执行、哪条已取消，执行率/取消率是多少；
- 计划写得够不够可判定，是否能在盘中被执行。

不回答：

- **不回答计划赚没赚钱**：`t_trade_plan` 没有金额与盈亏字段，要按代码去标的分析或统计总览看；
- 不回答「这笔成交算不算计划内」：统计页用的是成交上的 `is_planned`，与计划 ID、计划状态是两套口径；
- 不绑定账户、不占用资金、不校验代码/名称是否存在；
- 没有「部分执行」，也不能删除计划（只能取消，避免破坏执行率统计）。

## 2. 数据来源与查询条件

| 数据块 | 接口或表 | 过滤条件 | 何时刷新 |
| --- | --- | --- | --- |
| 新增表单 | `POST /plans` → `t_trade_plan` | 必填 `planDate`/`symbol`/`name`/`triggerDesc`/`actionDesc`；`reason` 可空；`status` 固定写入 `PENDING`；不校验日期是否为今天 | 点「保存计划」成功后清空文本并 `loadPlans(1)` |
| 计划列表 | `GET /plans?from=&to=&status=&keyword=&page=&size=` | `plan_date BETWEEN from AND to`（含端点，可空=不限）；`status` 精确匹配；`keyword` 对 `symbol` 或 `name` 做 LIKE（trim 后）；**不按账户过滤**；排序 `plan_date DESC, id DESC` | 首次进页签；点「筛选」；改「状态/每页」；关键字回车；点「重置」；保存/取消后 |
| 共 N 条 | 响应 `total` | 与列表条件一致 | 同上 |
| 取消 | `POST /plans/{id}/cancel` | 页面只在 `PENDING` 行显示按钮；接口不校验当前状态，重复取消仍返回 `CANCELLED` | 点「取消」后 `loadPlans(1)` |
| 状态变已执行 | 由「记成交」触发：`POST /trades` 带 `planId` → `TradeService.linkPlan` | 计划存在即置 `EXECUTED`；`planId` 不存在只记 warn，成交照常保存 | 本页不自动刷新，需点「筛选」 |
| 分页 | `page` 从 1；`size` 取 10/20/50 | 后端钳制 1~200，缺省 20 | 点分页或改「每页」 |

日期默认值：进页面填「今天−29 天」~「今天」。「重置」会把起止日期一并清空，等于不限区间。

## 3. 字段口径

| 字段 | 计算口径 | 来源 | 正常范围/参考 | 异常含义 |
| --- | --- | --- | --- | --- |
| 计划日期 | 表单必填，默认今天；列表按它过滤与排序 | `t_trade_plan.plan_date` | 当天或次日 | 填成历史日期=事后补计划，执行率失真 |
| 代码 | 原样保存，不校验格式、不校验行情存在性 | `symbol` | 6 位数字常见 | 带空格/后缀（.SH）会与标的页代码不一致，跳转选不中 |
| 名称 | 原样保存，不校验与代码是否匹配 | `name` | 与代码一致 | 与代码不符时列表仍按代码跳转 |
| 触发条件 | 自由文本，后端只校验非空；列表截断显示，悬停看全文 | `trigger_desc` | 含价格/均线/时间等可判定条件 | 只有「放量」「感觉」类描述=事后无法判定是否触发 |
| 动作 | 自由文本，只校验非空；建议含方向+价格+数量/仓位 | `action_desc` | 可直接照做 | 只写「买入/卖出」=无法执行也无法核对 |
| 依据 | 可空；空值不阻断保存，服务端只写 warn 日志 | `reason` | 一句可证伪的理由 | 为空=事后只能按结果归因，分不清体系还是运气 |
| 状态 | 新建=`PENDING`；成交关联后=`EXECUTED`；取消=`CANCELLED` | `status` | 三态之一 | 长期 `PENDING`=计划过期未收尾，会拉低执行率 |
| 操作 | 仅 `PENDING` 行渲染「取消」按钮 | 前端 | — | 已执行/已取消行无按钮，页面无法改回 |
| 共 N 条 | 接口 `total`，受筛选条件影响 | 响应 | — | 只看某状态时 N 是该状态数量，不是全部计划数 |
| 执行率/取消率 | 页面无聚合字段：按状态分别筛选后读「共 N 条」。执行率=`EXECUTED/全部`，取消率=`CANCELLED/全部`，待触发率=`PENDING/全部` | 前端计数 | 见 §6.2 | 分母必须同为「全部计划」且同一日期区间，否则不可比 |

### 3.1 合格计划的 5 要素检查表

| 要素 | 写在哪个字段 | 合格标准 | 不合格示例 | 代码是否强制 |
| --- | --- | --- | --- | --- |
| 触发条件 | `triggerDesc` | 可量化、可判真假：价格/均线/量比/时间点 | 「感觉要涨」 | 仅非空 |
| 动作 | `actionDesc` | 方向 + 价格区间 + 数量或仓位比例 | 「卖一点」 | 仅非空 |
| 依据 | `reason` | 一句话说明为什么是现在，且可被后续行情证伪 | 「看好」 | 否（允许为空） |
| 放弃条件 | `triggerDesc` 或 `actionDesc` 内（**无独立字段**） | 明确什么情况下今天不做 | 完全不写 | 否 |
| 日期 | `planDate` | 盘前填写，只对当天有效 | 填成上周/下周 | 非空，但不校验是否为今天 |

合格样例：「10:00 前站上 10.80 且量比 >1.5 → 买入 2000 股（约 15% 仓位），跌破 10.45 止损；不满足则当日不做」。五个要素都在两段文字里，能被行情逐条判定。

### 3.2 执行率/取消率怎么取数

1. 设 `from`/`to` 覆盖要统计的月份，状态选「全部」，读「共 N 条」= 分母。
2. 状态切「已执行」读 `E`；切「已取消」读 `C`；切「待触发」读 `P`。正常情况下 `E + C + P = N`。
3. 执行率=`E/N`，取消率=`C/N`，待触发率=`P/N`，均保留 1 位小数。
4. 页面没有「按状态一次返回三组计数」的接口，以上需要切换三次筛选；以接口返回的 `total` 为准。

## 4. 分析步骤

1. 进页签，「计划日期」默认今天；依次填代码、名称、触发条件、动作、依据，点「保存计划」。
2. 在返回对象里拿 `id`，去「记成交」：关联计划 ID 填该 `id`，「来源」选「计划内」；保存成交后计划自动变「已执行」。
3. 回到本页点「筛选」，确认状态已变；若当天没触发，点该行「取消」而不是放任挂着。
4. 通读「计划列表」（日期倒序），用 §3.1 的五要素逐行打勾，把不合格的行重写。
5. 「状态」选「待触发」+ 起始日期=今天，得到今天未收尾的计划数；超过 7 天的 PENDING 视为过期。
6. 按 §3.2 分别取三次「共 N 条」，算执行率、取消率、待触发率，并与上月同区间对比。
7. 对已执行计划，点代码跳标的分析，核对走势是否符合计划假设；不符的记进依据重写清单。
8. 结束时点「重置」清空筛选（含日期），回到不限区间视图。

## 5. 带数字的案例

以下为示例数据（2026-10，共 10 条计划）：

- 状态分布：6 条已执行、3 条已取消、1 条待触发 → 执行率 **60.0%**、取消率 **30.0%**、待触发率 **10.0%**；
- 6 条已执行里，4 条在记成交时同时填了计划 ID 并选「计划内」，2 条只填计划 ID、来源选了「计划外」→ 统计页这两条会落进计划外组，两套口径出现 2 条差；
- 3 条取消里，2 条的触发条件写的是「放量突破」且无价位，1 条写的是「跌破 18.20」但当天最低 18.26，没触发；
- 1 条待触发的计划日期是 10-08，已挂 20 多天未收尾；
- 其中一条合格计划写法：「10:00 前站上 10.80 且量比 >1.5 → 买入 2000 股（约 15% 仓位），跌破 10.45 止损」，五要素齐全，当天成交 2000 股并被置为「已执行」。

**现象**：执行率 60%、取消率 30%，但 3 条取消中有 2 条是条件不可判定，另 1 条是合理未触发；同时 1 条计划过期未收尾，直接拉低了执行率。

**结论**：60% 不能直接读成「自律不足」——一部分是写法问题（模糊条件），一部分是收尾缺失（过期未取消）；真正需要改的是触发条件与每日收尾动作，而不是加大自我要求。

**动作**：① 把「放量突破」全部改写为价格+量比+时间三条阈值；② 每天收盘前把未触发的当日计划显式取消；③ 成交时同时填计划 ID 并选「计划内」，保证执行率与统计页计划内外胜率同源；④ 下月目标：执行率 ≥80%、取消率 <20%，并观察计划内胜率是否高于计划外。

## 6. 判读表

| 现象 | 结论 | 动作 |
| --- | --- | --- |
| 执行率 <50%，取消率高 | 条件过宽或脱离盘面，计划不可执行 | 触发条件加价格/时间阈值，缩小单笔仓位 |
| 执行率 >85%，但计划外交易仍多 | 计划覆盖不足，只写了少数票 | 扩大计划覆盖面，把临时起意的票提前纳入 |
| 执行率高，已执行计划亏多 | 不是纪律问题，是计划方向错 | 点代码去标的分析与统计页，看计划内胜率 |
| 取消集中在「放量突破」类描述 | 条件不可判定，事后自我解释 | 改写为可量化条件，否则删掉这条计划 |
| 待触发长期积压（>7 天） | 没人收尾，执行率被稀释 | 每日收盘前取消当日未触发计划 |
| 执行率正常但计划内胜率不高于计划外 | 计划没有信息量 | 重写依据，只保留可证伪的理由 |
| 计划写了但从未填过关联 ID | 执行率恒为 0，统计页无计划内样本 | 记成交时补 `planId`，「来源」同步选计划内 |
| 同一天多条计划、代码重复且方向相反 | 盘前思路自相矛盾 | 合并为条件分支（若涨则…若跌则…） |

### 6.1 执行率/取消率判读方法

- 分母统一用「全部计划数」（`PENDING+EXECUTED+CANCELLED`），分子分别用三种状态；三者相加应等于分母，不等说明筛选日期或状态漏了。
- 参考带：执行率 70%~85% 且取消率 5%~20% 为健康；执行率 <50% 多为条件问题；执行率 >90% 且取消率极低，先怀疑是不是计划写得太少或太宽。
- 取消率高不等于错：因「价格未到」取消是纪律，因「看不懂条件」取消才是写法问题。回看被取消行的 `triggerDesc` 能区分。
- 必须按 `planDate` 同期对比（本月 vs 上月），不能按状态更新时间；后端不记录状态变更时间，页面上也拿不到。

## 7. 数据前提与常见问题

- 计划不绑定账户，顶部账户切换不影响本页数据。
- 计划日期只做筛选与展示，后端**不会自动过期**：不手动取消，`PENDING` 会一直计在分母里。
- 取消接口不校验当前状态。页面只给 `PENDING` 行按钮，但手工构造请求可把 `EXECUTED` 改成 `CANCELLED`，统计会因此偏。
- 成交填了 `planId` 只会把计划置为 `EXECUTED`，**不会自动把成交标成计划内**；`isPlanned` 缺省为 true，但在「记成交」里选「计划外」就会落进计划外组。
- 关联了不存在的计划 ID：成交仍保存，计划状态不变，只在服务端留 warn。
- 本页不自动刷新：在「记成交」关联计划后返回，需要点「筛选」或改状态/每页才能看到新状态。
- 没有删除、没有部分执行：一笔计划对应一次收尾；部分成交也算「已执行」。
- 排序按 `planDate` 倒序、同日按 `id` 倒序，不是按创建时间或状态变更时间。
- 关键字只搜索代码与名称，不搜索触发条件、动作、依据。

## 8. 联动

- 点列表里的代码 → `goSymbol(symbol)` 跳到「标的分析」并自动选中该票，用来验证计划假设是否成立。
- 计划本身不产生任何统计数字。统计总览的「计划内/计划外对比」消费的是成交表 `is_planned`（分组、算胜率与盈亏比），与 `plan_id`、计划状态**没有直接关系**。
- 想让「执行率」与「计划内外胜率差」互相印证：记成交时既填关联计划 ID，又把「来源」选「计划内」。只做其中一步，两套口径就会分叉。
- 计划的下游动作只有两个：去「记成交」关联执行，或在本页「取消」；已执行计划的状态无法回退。
- 本页不影响净值、回撤与标的统计；这些只由成交与每日复盘驱动。
